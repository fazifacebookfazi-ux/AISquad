## The threat landscape in late 2026: what actually happened

Before the checklist, the context. Three developments in the last few months changed the practical advice we give clients, so this is not a recycled version of a 2024 security post.

**Vite dev servers became a credential harvest.** F5 Labs reported in September 2026 that a mass-scanning campaign had been exploiting CVE-2026-39364 — a high-severity flaw (CVSS 8.2) in Vite versions 7.1.0 through 7.3.2 and the 8.x branch before 8.0.5 — to bypass the file-access protections that should have kept sensitive files out of reach. By appending query parameters like `?raw` or `?import&url&inline` to a request, an unauthenticated attacker could make the dev server return files its deny list was supposed to block, with an HTTP 200. From August into September, the scans hunted specifically for AWS credentials across common Linux home directories, Azure credential stores, Terraform state files, `serverless.yml` configs, and environment files — even using `/proc/self/cwd/.env` to grab the app's environment file without knowing its deployment path. Compared with 1,732 attempts over the previous three months, the August volume of 32,000+ attempts across 807 sessions was a sharp escalation. ([The Hacker News](http://thehackernews.com/2026/09/mass-scanning-campaign-exploits-vite.html), [InfoWorld](https://www.infoworld.com/article/4222246/exposed-vite-servers-are-being-probed-for-aws-and-azure-credentials.html))

**The npm worms keep coming back.** The original Shai-Hulud worm surfaced in September 2025: a self-propagating npm worm that poisoned popular packages with a `postinstall` payload, scraped npm, GitHub, AWS and cloud credentials from developer machines, and then used the stolen tokens to publish poisoned versions of *more* packages under the legitimate maintainers' identities. It kept evolving. A second wave hit in November 2025. In May 2026, the "Mini Shai-Hulud" campaign hijacked the TanStack router repository's CI workflow OIDC token, bypassed 2FA, and pushed malicious payloads into 42 packages across 84 versions reaching 12M+ weekly downloads. Then in August 2026, a variant tracked as ChainDrop compromised over 400 npm packages across 1,381 malicious versions with a combined reach exceeding 2 billion monthly downloads — exfiltrating developer credentials and re-publishing poisoned packages automatically. The response from the ecosystem: npm announced staged publishing, adding a review step before releases go live, following the attacks and a rocky migration off classic tokens.

**AI bots changed the attack surface too.** This one is adjacent but worth a sentence: your website now gets visited by legitimate and malicious AI crawlers at volumes nobody planned for, and blocking the bad ones while keeping the good ones is a real operational task in 2026 — we wrote a full playbook on [how to block AI bots from your website](/blog/how-to-block-ai-bots-website-2026) last month, and it pairs with this guide.

The pattern across all three developments is the same: the weak point is rarely the production application logic. It is the plumbing around it — dev servers, dependencies, secrets. So the hardening work follows that order.
## Door 1: dev servers exposed to the internet

This is the single most embarrassing and most common breach vector we see, and the Vite attacks made it a headline problem. Here is how it happens in practice.

Vite binds to localhost by default. Good. But then someone adds `--host` to the dev script so a teammate can preview on the office network, or a Docker container maps the dev port to the host, or a staging deploy runs the dev server "temporarily" while the production build is debugged. Each of those is a small convenience. Each one puts a server designed for local trust on a network where nobody is trustworthy. CVE-2026-39364 then turned that mistake into a credential leak: the flaw let attackers reach files through the `/@fs/` route that the deny list was meant to protect, simply by dressing up the request with `?raw`-style parameters.

Our rules, enforced on every project we ship:

- **Dev servers bind to localhost, full stop.** No `--host`, no `0.0.0.0`, no port mappings that widen it. If a designer or client needs to see progress, use a preview deployment (Vercel preview URLs cost you nothing) instead of exposing your laptop or a staging box.
- **Keep Vite patched.** If you are anywhere in the 7.1.0–7.3.2 or early 8.x range, upgrade past the fixed version now. More broadly: treat framework security releases the way you treat production deploys, not the way you treat routine dependency bumps. Our [Next.js 16 upgrade field guide](/blog/nextjs-16-upgrade-guide-2026) walks through how we plan framework upgrades so they do not break anything.
- **Keep `.env` files out of served directories.** The exploit specifically targeted environment files. Structure your projects so secrets live outside anything a dev server is allowed to serve, and confirm what `server.fs.allow` actually permits rather than assuming the defaults are tight.
- **Never run a dev server as your "staging" environment.** It is tempting. It is also how a credential scan finds a `.env.production` with live Stripe keys. Build for production or do not deploy.

The cost of this door being open is measured in hours, not weeks: scanners find exposed servers within days of them appearing. Close it today; it takes twenty minutes.
## Door 2: dependencies that run code on your machine

Every time you run `npm install`, you hand every package in your dependency tree the right to execute arbitrary code on your computer. That sentence should make you uncomfortable, because it is the entire Shai-Hulud story in one line.

The worm family's trick is disarmingly simple. A compromised package ships with a `preinstall` or `postinstall` hook. When you install — on your laptop, or worse, on your CI runner — the hook downloads a payload (the various waves used bundles ranging from ~727KB to 3.6MB) that scans the machine for secrets: npm tokens, GitHub personal access tokens, AWS credentials, Kubernetes configs, cloud CLI tokens. It exfiltrates them, then uses the stolen npm tokens to publish poisoned versions of *your* packages under *your* name, turning every victim into a new distributor. The August 2026 ChainDrop wave even planted persistence hooks in `.claude/settings.json` and `.vscode/tasks.json` so the malware re-ran whenever the developer opened their tools. Self-propagation means the attack does not need to be targeted at you. It just needs you to install something.

You cannot avoid dependencies — a modern web app has hundreds of transitive ones — but you can make your project hostile ground for this class of attack:

- **Commit your lockfile and enforce it in CI.** `npm ci` instead of `npm install` on every pipeline run. The lockfile is the one mechanism that guarantees the code you audited is the code that installs. Teams that let CI resolve fresh versions on every build are rolling the dice on every push.
- **Audit install hooks.** Before adding a new dependency, check whether it (and its transitive deps) ships lifecycle scripts: `find node_modules -name package.json -not -path '*/node_modules/*/node_modules/*' -exec grep -lE '"(pre|post)install"' {} \;`. A UI component library has no business running code at install time. If it does, that is a reason to look for an alternative, not a shrug.
- **Run `npm audit` on a schedule, not when you remember.** Wire it into CI with a sane threshold and make the build fail on high-severity advisories. Audits do not catch everything — the worm versions shipped faster than advisories for days — but they catch the known-bad, which is most of the volume.
- **Pin and verify the risky few.** Build tools, bundlers, and anything touching your deploy pipeline deserve pinned versions and a manual look at changelogs before upgrading. Compromise almost always arrives disguised as a routine version bump.
- **Separate your credentials from your dev machine.** Use short-lived tokens, scoped to the minimum permissions, for CI. If a worm lands on your laptop, a read-only npm token that expires in a day is a papercut; a full-access token you created two years ago is a catastrophe. This single habit is the difference between a contained incident and a self-propagating one.

The ecosystem is slowly hardening — npm's move to staged publishing, with a review step before releases go live, is a genuine improvement after the rocky migration off classic tokens. But platform-level fixes will not save a project that installs blindly. Your lockfile and your CI are the enforcement points you control.
## Door 3: secrets in the wrong places

The F5 scanning campaign did not just look for `.env` files. Its wordlists covered `terraform.tfstate`, `.terraform/` directories, `serverless.yml`, Azure credential stores, and the AWS credential files across every common Linux user home. That tells you exactly where developers habitually leave secrets: everywhere except a secrets manager.

Secrets hygiene is the least glamorous part of security and the part where we find the most mess during audits. The typical client repo we inherit has at least two of these problems:

- A `.env` file committed to git history at some point (even if removed later — history remembers).
- Production API keys in a shared Google Doc or a Slack thread from the launch week.
- Terraform state committed to the repo, which quietly contains database passwords, cloud access keys, and resource identifiers in plaintext.
- One "deploy key" or cloud service account with god-mode permissions, used by CI, three contractors, and the founder's laptop.

The fix is a ladder, and you climb it in order:

1. **Get secrets out of the repo.** Add every env file to `.gitignore`, then purge anything already committed — not just deleting the file, but rewriting history or rotating the exposed credentials, because "deleted" is not "unseen". If a key ever appeared in a public repo, assume it is burned and rotate it.
2. **Use a real secrets manager.** For AWS shops that is Secrets Manager or SSM Parameter Store; for everyone else, 1Password, Doppler, or your platform's built-in secret storage (Vercel environment variables, GitHub Actions secrets). The platform matters less than the property: secrets live in exactly one place, with access logs.
3. **Split secrets by environment.** Development, staging, production — separate values, separate access. The classic breach is a `.env.production` with live payment keys sitting on a developer's laptop next to a `.env` for local dev. If staging can never touch production keys, half the accident surface disappears.
4. **Scope and expire credentials.** Database users get only the permissions they need. CI tokens get the narrowest scope and a short lifetime. Human access goes through SSO with 2FA. The goal is that any single stolen credential is worth as little as possible to whoever steals it.
5. **Never commit Terraform state.** Remote state backends with encryption exist precisely because `terraform.tfstate` is a treasure map. Backend it, lock it, encrypt it.

## The foundation: the basics that are no longer optional

Once the three big doors are closed, the classic checklist items still matter. These are table stakes in 2026 — not because they stop sophisticated attackers, but because scanners test for their absence and move on when they are present.

| Measure | What to do | Why it matters |
|---|---|---|
| HTTPS everywhere | TLS on every page, HSTS header with a long max-age | Prevents credential interception on any network; HSTS stops protocol downgrade |
| Security headers | Content-Security-Policy, X-Frame-Options, Referrer-Policy | CSP in particular kills whole classes of XSS and injected-script attacks |
| Auth hardening | 2FA enforced for all admin/CMS accounts, rate-limited login, no default credentials | Stolen-password reuse is still the most common way admin panels fall |
| Backups you have tested | Automated daily backups, stored off-server, restored at least once a quarter | Ransomware and bad deploys both end the same way without a working restore |
| WAF + monitoring | A managed WAF in front of production, plus uptime and log monitoring with alerts | Defence in depth against novel probes; you find out about problems in minutes |
| Patch cadence | Framework and dependency updates on a fixed schedule, critical patches within 48 hours | Every month of delay widens the window attackers already know about |

Two of these deserve extra emphasis because clients consistently underinvest in them. **Backups** are not backups until a restore has been proven — we have inherited "daily backup" setups that had been silently failing for eleven months. And **patch cadence** fails without a pipeline: the teams that update fastest are the ones whose CI gives them confidence that an update will not break production. Fear of breakage is the real reason updates lag, so invest in the test pipeline and the patching problem half-solves itself.

## What to do if you think you are already compromised

Stay calm and work the list in order. Speed matters, but order matters more — rotating keys before removing the malware just gives the attacker fresh keys.

1. **Contain.** Take the affected machine or server offline or isolate it. If a dev machine ran a suspicious install, stop pushing to production from it immediately.
2. **Hunt for the worm's fingerprints.** Look for `preinstall`/`postinstall` hooks in your `node_modules`, oversized `bundle.js`-style payloads inside packages you did not write, `data.json` or `cloud.json` files that appeared without explanation, and a `shai-hulud-workflow.yml` file in your GitHub Actions directory. Search your repo history for `shai-hulud`, `trufflehog`, and `webhook.site` strings.
3. **Rotate everything that machine touched.** npm tokens, GitHub personal access tokens, AWS keys, cloud CLI tokens, database passwords, API keys — all of them, not just the ones you are sure were exfiltrated. Assume the harvester got everything it could read.
4. **Rebuild from clean sources.** Wipe `node_modules`, reinstall from your lockfile, and verify the lockfile resolves to legitimate registry tarballs. If the compromise reached CI, rotate those credentials too and re-run pipelines from a known-clean commit.
5. **Review what the credentials could touch.** Check cloud audit logs for unfamiliar activity in the window between the install and the rotation: new IAM users, changed policies, odd API calls. The credential theft is the means; what the attacker did with them is the actual damage.

Do not try to "watch and learn" what the malware does, and do not pay anyone who contacts you afterwards. Contain, rotate, rebuild, review.

## FAQ

**What is the most important thing to do to secure a website in 2026?**
Close the three doors attackers actually walk through: never expose dev servers to the internet, lock down your dependency supply chain with lockfiles and audits, and get secrets out of `.env` files and into a secrets manager. Those three cover the overwhelming majority of real-world compromises we see at the studio.

**How do I know if my website has been compromised through npm?**
Check for the tell-tale signs of the Shai-Hulud family of npm worms: install hooks in `node_modules` package.json files, oversized `bundle.js` payloads inside packages you did not author, `data.json` or `cloud.json` files that appeared in your project, and a `shai-hulud-workflow.yml` GitHub Actions file. Run `npm audit`, diff your lockfile against the registry, and rotate every credential that touched the machine.

**Is Vite safe to use after the 2026 credential-scanning attacks?**
Yes, if you keep it updated and never expose the dev server. The exploited flaw (CVE-2026-39364) only affected specific versions and only bit developers who exposed the dev server to the network. Patch, bind to localhost, and keep `.env` files outside served directories.

**Do small business websites really get hacked, or only big companies?**
Small sites get hit more, not less. The August 2026 F5 Labs data showed over 32,000 automated scan attempts in one month that do not discriminate by company size. If your server is reachable and has a weak point, you are in the wordlist.

**Should I use a WAF instead of fixing my website's security?**
A WAF is a seatbelt, not a steering wheel. It filters known-bad traffic, but it cannot fix an exposed dev server, a poisoned dependency, or secrets committed to a public repo. Do the hardening first, then add a WAF as defence in depth.

**How often should I update my website's dependencies?**
Monthly for marketing sites, every two weeks for anything handling user data or payments, and critical security patches within 24–48 hours. A lockfile plus a proper CI pipeline is what makes that cadence survivable.

## A note on AI-generated code and security review

One more 2026-specific door deserves its own mention, because it is new this year and we see it on nearly every inherited project: AI-written code that nobody reviewed for security.

Vibe coding and AI pair-programming have made it dramatically faster to ship. They have also normalised a workflow where large amounts of code enter a codebase that no human has read line by line. The models are good at producing code that works; they are inconsistent at producing code that is safe. We regularly find AI-generated auth checks with inverted logic, input validation that exists on the happy path and vanishes on edge cases, and — most commonly — error handling that helpfully leaks stack traces, database structure, or internal paths to the browser.

Our studio's rule for AI-assisted builds is simple: every AI-generated change goes through the same review a human's would, with security as an explicit review dimension. The teams that get burned are the ones who treated AI output as trusted because it looked confident. Confidence in prose is not evidence of correctness in code.

There is a cost angle here too. Clients sometimes ask whether AI-written code needs less security review because it was "generated by the latest model". Our answer is the opposite: it needs *more* review in the security dimension, because a model will happily write you a login form that works perfectly in the demo and stores passwords in reversible encryption. The demo is where the money is spent and the review is where it is saved. If your team is shipping AI-assisted code without a security-aware review step, add one this month — it is the cheapest insurance in this entire guide.

## The 2026 security posture, in one paragraph

Website security in 2026 is not about buying a bigger lock. It is about accepting that thousands of automated scanners probe your infrastructure every month, that your dependencies can turn against you, and that your own team's convenience habits are the most likely breach vector you have. The teams that stay safe are not the ones with the biggest security budgets; they are the ones with the dullest discipline — localhost dev servers, enforced lockfiles, secrets in one place, patches on schedule, backups that restore. Dull beats clever, every time.
