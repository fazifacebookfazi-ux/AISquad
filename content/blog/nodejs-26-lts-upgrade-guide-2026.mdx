On Wednesday 28 October 2026, Node.js 26 becomes the Active LTS release. For most teams that is a quiet calendar event. For yours, it should be the start of a short, disciplined upgrade — because this one is not just a version bump.

Node.js 26 is the last release under the old two-releases-a-year schedule, and the first release your team will adopt under a new rule: one major release per year, every release an LTS release, version numbers tied to the calendar year. The upgrade itself is small. The planning change around it is not.

There is also a sharper reason not to sit this one out. On 21 October 2026 the Node.js project shipped security fixes across all three supported lines — 22.23.4, 24.22.1 and 26.12.1 — including a high-severity Brotli decoder flaw that can permit remote code execution. If your app is still on an unpatched build, you are not behind schedule. You are exposed. The LTS promotion three days from now is the clean moment to fix both problems at once: move to a patched build and land on the line that will be supported until April 2029.

This guide is written from the studio floor. We run [Next.js](/services) and Node.js apps for clients in the US and Pakistan — you can read more about how we work on our [about page](/about) — we have shipped this exact upgrade path before — and we will tell you where it is boring, where it bites, and when to leave it alone.

## What actually happens on 28 October

Three things land on the same week, and it helps to keep them separate.

First, Node.js 26 is promoted from Current to Active LTS. That is the project's signal that the line is ready for production. Until now, 26 was fine for development and CI, but the conservative choice for long-lived workloads was 24. From 28 October, 26 takes that role.

Second, Node.js 24 drops from Active LTS to Maintenance LTS on 20 October. Maintenance means security and critical fixes only. Nothing breaks on the day, and 24 stays supported until 30 April 2028. But the direction of travel is set: new features stop, and the line starts its long wind-down.

Third, and strangest, for eight days — between 20 and 28 October — no Node.js version is in Active LTS at all. That gap is a scheduling quirk, not a crisis, but it tells you something useful about how this transition was planned: the old calendar and the new calendar overlap awkwardly, and teams that track LTS status by hand can easily misread the week.

Here is the release table that matters for planning, taken from the project's published schedule:

| Line | Status late October 2026 | LTS start | Maintenance start | End of life |
| --- | --- | --- | --- | --- |
| Node.js 20 | End of life | Oct 2023 | Oct 2024 | 30 Apr 2026 |
| Node.js 22 | Maintenance LTS | Oct 2024 | Oct 2025 | 30 Apr 2027 |
| Node.js 24 | Active LTS until 20 Oct | Oct 2025 | 20 Oct 2026 | 30 Apr 2028 |
| Node.js 26 | Current until 28 Oct | 28 Oct 2026 | 20 Oct 2027 | 30 Apr 2029 |
| Node.js 27 | Alpha from 28 Oct | Oct 2027 (planned) | — | 30 Apr 2030 |

Read that table once and the whole strategy writes itself: if you are on 24, you have until 2028, but the smart move is to upgrade while you have a full year of overlap. If you are on 22, you have six months. If you are on 20, you have already run out of time.

## The October security release you should not skip

Upgrades are usually about features. This one starts with a patch.

The October 2026 security release, published 21 October, covers all three supported lines. The headline flaw is CVE-2026-111497, an out-of-bounds write in the Brotli decoder bundled with Node.js, rated high. Applications that decompress Brotli data from untrusted sources using the zlib module are exposed, and the project says the flaw can permit remote code execution. That is the kind of sentence that should end a debate about timing.

The release also tightens two smaller behaviours you may notice in logs: connections to hosts written as non-canonical IP addresses, such as 0127.0.0.1, now fail certificate checks, and DNS resolve calls with a NUL character in the name now throw. Neither is a breaking change for a well-behaved app, but both are the sort of thing that shows up in an error tracker the morning after a deploy and gets blamed on the upgrade. Knowing they come from the security release, not from 26 itself, saves a wasted rollback.

The fixed versions are 22.23.4, 24.22.1 and 26.12.1, and the official Docker images for all three lines were published on 21 October. If you run Docker in production, rebuilding your images is the fix — a version bump in a Dockerfile that nobody rebuilds changes nothing.

One more point, because it catches teams out: Node.js 20 is affected by these vulnerabilities and receives no fix. End-of-life versions are always treated as affected when a security release lands. If your organisation still runs 20 anywhere — a legacy admin panel, a cron worker nobody owns, a client's old VPS — that box is now unpatchable by design. Upgrading it is no longer a nice-to-have.

Our own rule, borrowed from years of [website security work](/blog/how-to-secure-a-website-2026), is simple: a security release that touches your runtime is a same-week job, not a next-quarter job. The LTS promotion just happens to make this particular same-week job unusually convenient.

## What breaks when you upgrade to Node.js 26

Good news first: for most applications, the breaking list fits on a sticky note. The Node.js 26.0.0 release notes list five items that matter, and all five are searchable before you ship.

| Breaking change | What it means | How to find it |
| --- | --- | --- |
| Private `_stream_*` modules removed | Imports like `_stream_readable` no longer work | Search for `_stream_` in your code and dependencies |
| `res.writeHeader()` removed | The misnamed alias is gone; `res.writeHead()` is the correct call | Search for `writeHeader(` |
| `--experimental-transform-types` flag removed | Plain TypeScript type stripping still works, but if you relied on this flag for enums, namespaces or decorators, you need a real compiler | Search your start scripts and CI config for the flag |
| `module.register()` deprecated | Custom loader hooks still work but now emit a runtime deprecation warning | Run tests with `--trace-deprecation` and watch the output |
| Native addon ABI change | Prebuilt native binaries must be rebuilt for Node.js 26 | Rebuild after the version bump; watch for `NODE_MODULE_VERSION` errors |

Two observations from doing this in practice. First, the breakages almost never live in your own code. They live in old dependencies — a logging library last updated in 2023, a PDF tool with a pinned native binding, an internal utility copied between projects for years. That is why the search step matters more than the version bump itself: you are auditing your dependency tree, not your code.

Second, the deprecation warning on `module.register()` is the one that surprises teams. Nothing fails. Your test suite just gets noisier, and someone on the team spends an afternoon wondering whether the noise is a problem. It is not, yet. But it is a signal that loader hooks are on the way out, and if your app depends on them heavily, you should plan that migration separately rather than letting it ride inside a runtime upgrade.

Under the hood, 26 also brings V8 14.6 and Undici 8, the HTTP client behind the built-in `fetch()`. Both bring performance improvements without API changes. You will not feel them as a feature, but on API-heavy workloads — the kind of backend that calls three services to render one page — the fetch improvements are the quiet reason to upgrade even if nothing else changed.

## Three starting points, three different upgrades

Where you start decides how much work this is. Be honest about which row you are in.

### From Node.js 24: the comfortable upgrade

This is checklist work, not refactoring work. Bump the version, rebuild native addons, search for the five breaking items, run the test suite with `--trace-deprecation`, and deploy behind a staged rollout. In our studio's observed range, a single app on 24 takes half a day to two days of engineering time, including the test run and the staged deploy.

If you are on 24 and your app is healthy, there is no reason to wait. You have until April 2028 on 24, but every month you wait is a month less overlap with 26, and overlap is what makes an upgrade safe. Upgrade while both lines are supported, not after one of them stops being.

One more thing worth checking on the 24-to-26 path: TypeScript. Node.js 24 made type stripping stable, and 26 keeps it, but the removal of the `--experimental-transform-types` flag catches teams that leaned on it for enums, namespaces or decorators. If your project runs TypeScript files directly with Node.js and no build step, grep your start scripts for that flag before you upgrade, and decide now whether those language features need a real compiler in your pipeline. For most Next.js and bundled apps this is irrelevant — the bundler handles it — but for small API services that run raw TypeScript, it is the one 26 change that turns into real work rather than a search-and-replace. The fix is usually small: either drop the flagged features or add a lightweight build step. Either way, find out in staging, not on deploy day.

### From Node.js 22: the upgrade with a deadline

From 22 you absorb two rounds of changes at once: everything that changed in 24 (V8, permissions, minimum glibc) plus everything in 26. The list is longer, but it is still a known list, and the same five searches plus a dependency audit cover most of it.

The real difference is the deadline. Node.js 22 reaches end of life on 30 April 2027 — about six months from now. Teams that leave this until March will discover that their test environments, their Docker images and their CI matrices all need the same change in the same week. Start in November or December, when you can afford a slow rollout and a revert.

### From Node.js 20 or older: stop reading and start moving

Node.js 20 has been end of life since 30 April 2026. There is no supported path that keeps you on it. The upgrade from 20 to 26 crosses three major versions, and for apps that old the runtime bump is usually the smallest part of the job: the dependency tree, the TypeScript setup and the deployment pipeline all need attention at the same time.

If you are in this row, do not try to do it as a single heroic deploy. Upgrade to 24 first, stabilise, then move to 26. Two small, reversible steps beat one large, frightening one, and each step gives you a working deploy to fall back to. This is also the row where hiring outside help pays for itself fastest: a studio that has done the jump before will find the landmines in your dependency tree in a day that would take your team a week of evenings.

## The upgrade checklist we actually run

Theory is cheap. Here is the sequence we follow on client projects, in order, with nothing skipped.

**1. Inventory before you touch anything.** Run `node --version` on every environment that matters: local machines, CI, staging, production, cron workers, Docker images. You will find at least one you forgot. Write the list down.

**2. Search for the five breaking items.** Run the searches from the table above across your source and your dependencies. If a dependency is the culprit, check whether a newer version exists before you write a workaround. Nine times out of ten, it does.

**3. Pin the new version explicitly.** Set `.nvmrc`, your Dockerfile base image and your CI matrix to `26` — a major line, not `latest` and not a floating tag. Floating tags are how a routine rebuild silently jumps a major version at 2am. This matters more under the new release schedule, where the meaning of tags like `lts` is still being worked out by the Docker image maintainers.

**4. Rebuild native addons.** After the version bump, rebuild. If you see `NODE_MODULE_VERSION` errors, that is the addon ABI change doing exactly what it is supposed to do. Rebuild, do not downgrade.

**5. Run the full test suite with `--trace-deprecation`.** This surfaces the `module.register()` warnings and any other deprecations your app has been quietly accumulating. Fix what is cheap, log what is not, and do not let a warning you already understood block the deploy.

**6. Deploy to staging first, then a slice of production.** Canary the upgrade if your setup allows it: a fraction of traffic on 26, the rest on the old line, with error rates compared side by side. Roll back on error rate, not on vibes.

**7. Rebuild your Docker images.** The October security fix only reaches you through a rebuilt image. Tag the rebuild, keep the old image, and confirm the running container reports 26.12.1 or later.

**8. Update the docs nobody reads.** Your runbook, your onboarding guide, your client's handover document — all of them name a Node.js version somewhere. Update them now, while the change is fresh, or the next person to onboard will install the wrong version and lose a morning.

That is the whole process. It is not glamorous, and that is the point: a runtime upgrade should be boring. If it is exciting, something went wrong earlier.

## Hosting and deployment gotchas

The runtime is only half the story. Where your app runs decides how smooth the upgrade feels, and this is where we see the most avoidable pain.

**Managed platforms do the easy part.** On Vercel, Netlify and similar platforms, the Node.js version is usually a setting or a field in your project config, and the platform handles the rest. If your site is a [Next.js](/blog/nextjs-16-upgrade-guide-2026) app on Vercel, the upgrade is mostly a config change plus a redeploy. Check the platform's supported-versions page first: platforms adopt new LTS lines on their own timetable, and deploying a version your platform does not offer yet produces a confusing build error, not a helpful message.

**Docker is where discipline pays.** Pin the base image to a major line (`node:26`), rebuild after the security release, and keep the previous image tagged and available. The Docker image project has not yet published a final decision on what `lts`, `current` and `latest` will mean under the new annual schedule, or whether alpha builds get images at all. Until it does, explicit pins are not pedantry — they are the only guarantee your next rebuild does not change your runtime.

**Shared hosting and VPS setups are where old versions hide.** If your app runs on a VPS or a shared host, the Node.js version on that box is whatever someone installed when the app was built, and nobody has touched it since. Check it before you plan anything else. We have seen upgrades stall for a week because the production box was still on a version the developer's laptop had left behind two years earlier. This is also the setup where [hosting choice](/blog/where-to-host-your-website-2026) matters most: a host that lets you pick your runtime version is worth more than a slightly cheaper one that does not.

**CI matrices multiply the work.** If your CI tests three Node.js versions, the upgrade means updating the matrix, not just the app. Drop the version you are leaving behind from the matrix at the same time you add 26, or you will be maintaining a test grid for a runtime you no longer support.

**Version managers save the local mess.** Developers rarely run one Node.js version. A laptop that serves three client projects probably has three runtimes, and the upgrade is where that quietly falls apart: one project pinned to an old `.nvmrc`, another relying on a global install nobody remembers setting up. Use a version manager — nvm on macOS and Linux, fnm on Windows — and pin per project with `.nvmrc` or `.node-version`. Then the upgrade is a file change in each repo, not a machine rebuild. For teams in Pakistan working across US client projects and local products, this is also the cheapest form of consistency you can buy: every developer, every CI runner and every staging box reads the same file and installs the same runtime. When a new hire joins and asks which Node.js version to install, the answer should be a file in the repo, not a message in a group chat.

## The bigger change: one release a year, every release LTS

Step back from the upgrade itself, because the schedule change is the part that will still matter in 2029.

From Node.js 27 onward, the project ships one major release per year, each April, and every release becomes LTS the following October. The six-month alpha phase runs October to March, and alpha builds carry names like `27.0.0-alpha.1`. Alphas are for testing, not production, and the project explicitly asks library authors to run them in CI.

The project says the change comes from years of data about how people actually use Node.js, and from the reality that Node.js is maintained mostly by volunteers. Fewer release lines means less maintenance work, and a simpler choice for users: run the latest LTS. That reasoning is sound, and it is good news for small teams, because the old two-releases-a-year rhythm quietly taxed everyone who maintained a version matrix.

For your planning, the practical effect is a predictable yearly rhythm: test the new version from April, upgrade production after it becomes LTS in October. Budget one migration window a year, treat it as scheduled engineering rather than an emergency triggered by an end-of-life notice, and put it on the calendar now. Teams that do this never have a Node.js emergency. Teams that do not have one every eighteen months, like clockwork.

Two things to watch as the new model settles. First, the tooling around version selection — Docker tags, `lts/*` aliases in version managers, platform defaults — has not fully caught up with the new schedule. Expect a year of small inconsistencies, and pin explicitly until they resolve. Second, the alpha phase is a gift to library authors and a trap for everyone else. If you maintain shared internal packages, wire the alpha channel into CI so breaking changes surface during the six-month alpha rather than after the Current release ships. If you build applications, ignore alphas completely. Your job is to run LTS, and the alpha phase exists so that by the time a release reaches you, someone else has already found its problems.

## Frequently asked questions

### When does Node.js 26 become LTS?

Node.js 26 becomes Active LTS on 28 October 2026. It was first released on 5 May 2026, moves to Maintenance LTS on 20 October 2027, and reaches end of life on 30 April 2029. If you run production workloads, 28 October is the date your upgrade window opens.

### Is Node.js 26 a breaking upgrade from Node.js 24?

For most applications, no. The breaking list is short: removed private _stream_* modules, the removed writeHeader() alias, the removed --experimental-transform-types flag, a new deprecation warning on module.register(), and a native addon rebuild. All five are easy to search for before you deploy.

### Should I upgrade from Node.js 22 or wait?

Start now and finish before April 2027. Node.js 22 reaches end of life on 30 April 2027, and the jump from 22 absorbs two rounds of changes at once. If your app is on 22 today, plan the upgrade for November or December 2026, not for the week the deadline arrives.

### What does the October 2026 Node.js security release fix?

The October 2026 security release fixes several vulnerabilities, the most serious being CVE-2026-111497, an out-of-bounds write in the bundled Brotli decoder rated high, which can permit remote code execution in apps that decompress Brotli data from untrusted sources. The fixed releases are 22.23.4, 24.22.1 and 26.12.1.

### What happens to the odd and even Node.js release rule?

It ends with Node.js 26. From Node.js 27 onward there is one major release per year, every April, and every release becomes LTS the following October. Version numbers will match the calendar year: 27 in 2027, 28 in 2028. The old advice to run only even-numbered releases no longer applies.

### Can I still run Node.js 20 in production?

You should not. Node.js 20 reached end of life on 30 April 2026 and receives no security fixes, including the October 2026 fixes. Every month you stay on it, the gap between your runtime and the patched releases grows, and auditors and clients notice.

### How much does a Node.js upgrade cost?

In our studio's observed range, a straightforward upgrade for a single app costs roughly $400–$1,500 (PKR 120,000–450,000), covering the version bump, dependency rebuild, test run and staged deploy. Apps with native addons, old TypeScript setups or pinned Docker images land at the higher end, and multi-service estates are quoted per service.
