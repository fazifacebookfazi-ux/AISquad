On 15 October 2026, Figma used its first Config event in India — in Bengaluru, with more than 30,000 registrations — to announce the biggest change to its canvas since multiplayer cursors. Code Layers left private beta and opened to everyone. Your design file can now hold running code, not just pictures of code's output.

We've spent the last week working inside the open beta on client projects, and here's the honest read: this is the most consequential Figma release of 2026, and also the easiest one to misuse. It does not delete the design-to-development handoff. It relocates it, prices it in AI credits, and hands it to a team that is not ready to own it. This guide explains what Code Layers actually does, what the 15 October announcement really changed, what it will cost you after the free window closes, and our verdict on who should adopt it now.

If you're a founder or product lead rather than a designer, the short version is this: your design file is about to start containing working software, and the question of who is responsible for that software's quality just got more complicated. Read on for the parts that affect your budget and your timelines.

## What Code Layers actually is

A Code Layer is a layer on the Figma canvas that contains running code. Not a screenshot. Not a prototype link pretending to be interactive. Actual code you can click, type into and edit, sitting next to your design frames in the same file.

You can duplicate a Code Layer, ask Figma's agent to develop a different direction from it, and compare two working versions side by side — without leaving the file. You can also run the whole thing in reverse: pull a running prototype onto the canvas and extract editable design layers from it, capturing individual states of a flow as real design frames you can inspect and annotate.

This is different from everything Figma already shipped in this space:

- **Prototype mode** connects static screens with arrows. It can never show you what a component does when data is real, because the data isn't.
- **Figma Make** (prompt-to-app) generates an app from a description. It's a generator; Code Layers is an environment. Make gives you a thing; Code Layers gives you a place to work.
- **Dev Mode** hands developers specs, assets and code snippets from a design. It's a handoff surface; Code Layers moves the code upstream into the design file itself.

The distinction matters because each of these assumed a boundary between designing and coding. Code Layers is Figma betting that the boundary is gone, and that the canvas should hold both sides. CEO Dylan Field [described the direction](https://globalbusinessline.com/figma-launches-code-layers-and-new-ai-powered-features-at-config-india-2026-deepens-india-expansion/) as a "full-stack creative canvas where teams and agents can build together, from idea to ship, in a visual-first way."

## How it works: the five ways into a Code Layer

There are five documented entry points, and they matter because each one implies a different team workflow.

### 1. Prompt Figma's agent from an existing design

Start with a design frame, prompt the agent, get a working prototype. This is the path most teams will try first — it's the fastest route from what you already have to something clickable. Figma [made its on-canvas agent generally available](https://www.webpronews.com/figma-draws-new-lines-for-ai-agents-with-specs-code-layers-and-shared-rules/) on 6 October 2026, a week before Config India, with faster performance and better context pulling across files. Its internal tests claim the agent now wins more than 60% of human-graded evaluations against professional designers — take that with the usual vendor-grade scepticism, but it tells you where Figma thinks this is heading.

### 2. Import from a GitHub repository

This is the one we find most interesting, and the least discussed. A team can pull an existing coded interface — real production code — onto the canvas and review it as a design. Designers who never open the repo can now comment on the actual built interface. For studios like ours, where [our design work](https://www.aisquadx.tech/services) already ships as code, this closes a loop that has been open for years: the review happens on the thing users touch, not on a picture of it.

### 3. Connect a coding agent through the Figma MCP

Figma's Model Context Protocol server got faster with more surfaces at Config India, and now supports generating Code Layers and reading or writing Specs from inside external AI tools. Twenty new MCP partners launched, including [OpenCode](https://www.webpronews.com/figma-draws-new-lines-for-ai-agents-with-specs-code-layers-and-shared-rules/) (which feeds design-system context to coding agents and sends prototypes back to Figma for review) and India's Sarvam AI. If your engineering team lives in Cursor or Claude Code, this is the route that keeps Code Layers in their existing flow rather than adding another tool.

### 4. Start from a blank code layer

For net-new explorations: spin up an empty layer, prompt your way to a working component. Useful for early-stage interaction ideas where designing frames first would slow you down.

### 5. Capture a live webpage with the Chrome extension

Point Figma's Chrome extension at a live website and capture it onto the canvas as a starting point. Competitive teardowns just got significantly faster — though you should think carefully about what "starting point" means for your own IP hygiene.

## What actually changed on 15 October

Code Layers was the headline, but Config India shipped a bundle. The other pieces are what make Code Layers usable in a real team, so don't evaluate them separately:

- **Figma Specs** (open beta, Professional/Organisation/Enterprise): a Markdown-based editor for documenting your design language so both humans and AI agents work from the same rulebook. We covered this in depth in our [Figma Specs guide](/blog/figma-specs-explained-2026) — Specs is the context layer that stops Code Layers from generating off-brand nonsense.
- **Guidelines** (open beta, Professional/Organisation/Enterprise): published design-library rules that the agent reads on every prompt when the library is enabled. This is the enforcement mechanism; Specs is the documentation, Guidelines are the law.
- **Code sources** (closed beta, selected participants): import from GitHub repositories or npm packages so the agent draws on your real production components. This is the piece that turns Code Layers from a prototyping toy into something a design system team can trust — and it's the piece you can't have yet.
- **Centralised design systems** (preview): bundles libraries, code and guidelines together. Not generally released.
- **Payload as a native backend for Figma Make**: CMS, database, APIs, authentication and file storage inside the same workflow.
- **Figma MCP expansion**: the MCP server is faster, supports more surfaces, and can now generate Code Layers and read or write Specs from inside external AI tools. Twenty new partners joined, including OpenCode — which feeds design-system context to coding agents and sends prototypes back to Figma for review — plus Sarvam AI and Grok Bot. If your developers live in Cursor or Claude Code, the Figma context now travels with them instead of being locked in the design file.

Read the bundle together and the strategy is obvious: Figma is racing to make sure AI-generated UI is constrained by your rules before it's generated at all. Context in, behaviour out. That's a smart bet, and it's also an admission — without the constraints, the generated output wanders.

## The pricing reality: free now, metered from 5 November

Here's the detail most coverage buried. Creating and editing Code Layers is **free on paid plans through 4 November 2026, inclusive**. After that, these tasks consume AI credits, and the amount scales with task complexity. Other agent actions may already consume credits.

Figma hasn't published a per-task price list in the launch materials, so any article quoting you an exact per-prototype price is guessing. What we know from the announcement:

1. The free window is a trial, not a pricing decision. It's 20 days, and it's designed to get you hooked before the meter starts.
2. Pricing is usage-based and opaque until it isn't. "Depends on task complexity" means your bill depends on how your team prompts.
3. This lands on top of paid plans. You need a Professional, Organisation or Enterprise seat to play at all.

For context on what this means in real money: our studio's observed range for Figma spend in small Pakistani agencies is $15–45 USD per editor per month today (roughly PKR 4,200–12,600 at current rates). AI credit overages will stack on top of that. If your designers start treating the agent like a junior developer — generating and regenerating prototypes all day — your Figma bill stops behaving like software and starts behaving like cloud compute. Set a credit budget before your team discovers the feature, not after finance asks questions.

A practical way to size it: during the free window, log every Code Layer generation and edit per project for two weeks. Count tasks, not hours. If a typical landing page prototype takes 15–25 agent actions across revisions, you have a baseline for what the meter will charge once it starts. Multiply by your monthly project volume and you have a budget number you can defend — or a reason to keep prototyping in a cheaper tool and reserve Code Layers for client-facing reviews only.

## What it breaks: the new handoff problem

The design-to-development handoff has been the industry's open wound for a decade. Our [Figma-to-code workflow guide](/blog/figma-to-code-workflow-2026) walks through how we currently bridge it. Code Layers doesn't heal the wound. It moves it.

Figma's chief design officer Loredana Crisan [told TechCrunch](https://devops.com/figma-gives-ai-agents-a-spec-sheet-and-developers-a-shared-canvas) that teams now produce 17 times as many lines of code as before, but only 1.3 times as many releases. Most of that code exists to figure out what the product should be, not to ship. Code Layers is Figma's answer to where that exploration should happen: on the canvas, where everyone can see it, comment on it, and — critically — decide which of the 17x is worth keeping.

That's a genuine improvement. But it creates three new problems that nobody is talking about yet.

### Who owns the prototype code?

When a designer prompts an agent into a working prototype, who reviews the code? In our studio, that question now has an uncomfortable answer: the developer has to review prototype code that was never meant for production but will absolutely be copy-pasted into it. Code Layers code is "real" enough to run and "temporary" enough to be sloppy. Teams need a rule — ours is that nothing leaves a Code Layer without a developer pass — or prototype shortcuts will fossilise into production debt.

### The review burden moves, not shrinks

A [Figma-run randomised trial](https://research.breon.ai/) (100 participants, arXiv, 22 September) found that product managers finished UI tasks 35% faster with Figma Make, while designers showed no significant aggregate time saving — their only real gain was building interaction prototypes 26% faster. The leverage is in widening who can produce UI, not in speeding up people who already could. Code Layers extends that pattern: your PMs and marketers can now generate working prototypes. That means designers spend more of their week reviewing other people's generated work. That's a real job, and it needs to be recognised as one — in job titles, in time allocation, in compensation. Only [28% of design leaders](https://research.breon.ai/) have updated evaluation or compensation to match the expanded scope.

The practical consequence for studios: your design review meetings change shape. Instead of walking through static screens, you're clicking through behaviours — and behaviour review is slower, because you have to test the edge cases, not just look at the happy path. Budget review time accordingly. A prototype that took ten minutes to generate can take an hour to properly evaluate, and the evaluation is where the quality actually lives.

### The 60% problem

Figma's claim that its agent wins 60%+ of human-graded evaluations against professional designers sounds impressive until you ask what "wins" means in a graded evaluation. Nobody's production incident has ever been caused by a graded evaluation. Before you let agent-generated Code Layers near a client project, run your own test: have the agent rebuild one of your shipped components, then have a senior engineer review it blind. We did. The results were instructive enough that we wrote new rules about it.

## Our verdict: who should adopt now

## Setting up a Code Layers workflow that won't collapse

If you're adopting, do it with rules. Here's the setup we'd recommend to any team, based on our first week in the beta:

1. **Write a Specs doc before you generate anything.** Code Layers without constraints produces median output. Document your tokens, your component rules and your tone in Specs first — [our Specs guide](/blog/figma-specs-explained-2026) shows how. The 26% prototyping speedup the trial found only materialises when the agent isn't guessing your design system.
2. **Publish Guidelines for every library the agent touches.** Guidelines are read on every prompt when the library is enabled. This is your cheapest quality control.
3. **Assign a code owner for every Code Layer.** Name the engineer who reviews it. No owner, no merge into anything real. Prototype code rots fast and gets copied faster.
4. **Set an AI credit budget per project.** Decide now what a prototype is worth to you in credits, before the 4 November meter starts. Track it for two weeks during the free window so the meter doesn't surprise you.
5. **Run the blind review test.** Agent-rebuild one shipped component, senior engineer reviews it blind, compare against your human-built version. Do this before client work, not during it.
6. **Keep the extraction habit.** The reverse direction — pulling a running prototype back into editable design layers — is the sleeper feature. Use it to capture the states your user testing actually validated, so the reasoning survives even if the code doesn't.
7. **Version your prompts, not just your designs.** When the agent produces a direction worth keeping, save the prompt and the Specs state alongside the layer. Regeneration is only reproducible if you know what you asked for.
8. **Decide the exit path per prototype.** Before generating, agree what happens to this layer: throwaway exploration, client review artefact, or candidate for production rebuild. Most Code Layers should be throwaway. The ones that aren't need the code owner's sign-off in writing.
